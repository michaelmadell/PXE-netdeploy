# 16. Jobs: rows as the queue, an in-process runner, no resume

Status: accepted

## Context
Imports (ISOs, driver packs) and boot image builds take minutes and return
`202` with a `Job` (spec conventions). The spec already says builds run one at
a time per host (DISM mount directories don't tolerate parallel builds) and
that a second build of the same boot image returns `409 build_in_progress`.
This records how jobs are stored, queued, run, cancelled and recovered.

## Decision
- **The `jobs` table is the queue.** A job row is inserted in the same
  transaction as the resource it works on (an `importing` image, a `building`
  boot image), then the runner is woken. IDs are ULIDs, so ordering by id is
  first in, first out. Queued jobs survive restarts and run afterwards.
- **One active job per resource**, enforced by a partial unique index on
  `resource_id` for `queued`/`running` jobs. This gives `build_in_progress`
  and the same rule for imports.
- **An in-process runner with lanes**: `build` runs one job at a time,
  `import` two. Any number of jobs can be queued; each lane takes them in
  order. Limits are constants for now.
- **Each kind registers `Run` and `Abandon`.** `Run` does the work with a
  context cancelled on cancel or shutdown, reports progress, and leaves its
  resource in a final state (e.g. `failed`) before returning an error.
  `Abandon` fixes up the resource of a job that never ran its own cleanup: a
  queued job that was cancelled, or a job interrupted by a restart.
- **Outcome**: nil is `succeeded`; an error carrying a Problem code (e.g.
  `insufficient_storage`) is `failed` with that code; any other error is
  `failed` with `internal_error`; a cancelled context is `cancelled`.
- **Cancel**: a queued job is cancelled at once; a running job gets
  `cancelRequested` and its context cancelled, and becomes `cancelled` when
  `Run` returns.
- **No resume.** At startup every job still `running` becomes `failed` with
  `interrupted` and its kind's `Abandon` runs; staging files were already
  removed by the content store (ADR 0015). Extraction and DISM builds have no
  safe midpoint and are cheap to restart from scratch, so the admin retries.
- **Progress** is kept in memory and written to the row, with a `job.updated`
  event, at most twice a second per job; status changes are written and
  published immediately.
- **Retention**: finished jobs are deleted 30 days after they finish, by the
  hourly purge loop. Queued and running jobs are never deleted.
- `content.publish` is removed from `Job.kind`: nothing defined it.

## Consequences
- A crash mid-import leaves a `failed` image with `interrupted`, not a stuck
  `importing` one.
- A job that crashes the server fails once instead of retrying forever.
- Raising the lane limits later (or making them settings) needs no schema
  change.
- Jobs are not resumable; a 10 GB ISO import interrupted near the end starts
  again.
